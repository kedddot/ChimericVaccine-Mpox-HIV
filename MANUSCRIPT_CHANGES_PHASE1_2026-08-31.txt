C1. [DISCLOSE] THE SECOND ALLERGY PREDICTOR COVERS ONLY 57 OF 184 CANDIDATES.
    AllergenFP cannot compute its fingerprint below 16 amino acids. Of the 184

C2. [DISCLOSE] *** ALLERTOP IS NEAR-RANDOM AT THIS STUDY'S PEPTIDE LENGTHS. ***
    This is the single most important addition to the paper.
    AllerTOP v2 was reimplemented from its own published method and its own
    distributed training set (2,426 allergens + 2,426 non-allergens), then
    measured at this study's exact candidate lengths, with each test peptide's
    PARENT PROTEIN HELD OUT of the reference so it could not vote for its own
    fragment:
        peptide length    balanced accuracy
             9 aa              58.7%
            10 aa              55.9%      <-- chance is 50%
            15 aa              62.7%
            16 aa              65.1%
        full-length proteins   88.9%   (published figure: 88.7%)
    CONSEQUENCE FOR THE RESULTS: 57 of the 76 allergenicity exclusions -- 75%
    of them -- were made by AllerTOP ALONE, on peptides of 9, 10 and 15 aa.
    These CANNOT be presented as confident allergenicity calls. They are the
    cited method applied as specified, at a length it was not built for.
    THE VALIDATION THAT MAKES THIS CITABLE: the reimplementation was tested
    against the live AllerTOP server under a PRE-REGISTERED, HASH-VERIFIED
    BLIND PROTOCOL -- predictions for 153 peptides were frozen to disk and
    hashed BEFORE those peptides were submitted. Result: 148/153 = 96.7%
    agreement (majority-guess baseline 56.9%). Accuracy ROSE as the blind set
    grew (93.5% on 31 -> 95.4% on 65 -> 96.7% on 153), which is the opposite
    of what an overfitted model does.
    The reimplementation generated NONE of the study's verdicts -- all 184 are
    transcribed from the real server. That separation is what makes the 96.7%
    a clean measurement rather than a circular one.

C3. [DISCLOSE] THE TWO ALLERGY PREDICTORS AGREE ONLY 49% OF THE TIME.
    Measured on this study's rebuilt pool: AllerTOP and AllergenFP agree on
    18 of the 37 16-mers where both can run. They disagree MORE OFTEN THAN
    THEY AGREE.
    Two predictors that agree half the time are not independent confirmation,
    and either one alone is close to a coin toss.
    THIS REPLACES the old "59% disagreement" figure, which came from the

    CONSEQUENCE: exclusion requires CONSENSUS (deviation #24). Under the old

C4. [DISCLOSE] THE HUMAN SELF-SIMILARITY SCREEN, AS PUBLISHED, CANNOT DETECT

D3. [NEW DEVIATION] HUMAN SELF-HOMOLOGY SCREEN RESTRUCTURED INTO TWO LAYERS.

    LAYER 2 -- exact contiguous-identity screen against the same human

        window 9+  real  0.0%   scrambled  0.2%   no positives either way

        70%/70%   real 24.1%   scrambled 25.2%
        75%/75%   real 20.4%   scrambled 18.5%
        80%/80%   real  2.8%   scrambled  4.8%

    Loosening BLAST to obtain exclusions would have deleted 26 of 108

G3. [NEW DEVIATION, RESOLVED] CROSS-CLASS SELECTION PRIORITY WAS CHANGED,
    DELIBERATELY, AND THE CONSTRUCT WAS REBUILT.
    ORIGINAL DEFECT: when two epitope classes claimed the same genomic
    region, the selection routine's fixed iteration order
    ("MHC-I", "MHC-II", "B-cell") meant MHC-I always won, by accident of
    tuple order rather than immunological judgment. Measured consequence in
    the first rebuilt construct: all 6 surviving HIV_gp41 B-cell candidates,
    including the MPER-proximal region that carries HIV-1's best-
    characterised broadly neutralising antibody epitopes, were displaced by
    a single MHC-I epitope.
    DECISION: the order was changed to ("B-cell", "MHC-II", "MHC-I") --
    antibody-target and helper-T-cell epitopes now outrank killer-T-cell
    epitopes when two classes contest one region. Rationale: B-cell epitopes
    are the direct antibody targets, and MHC-II is required for the CD4+
    help that antibody maturation and the paper's own GPGPG helper block
    depend on. MHC-I is not removed as a class -- only demoted in this
    specific tie-break.
    THE CONSTRUCT WAS REBUILT under the new rule (same 6,000-trial search,
    same seed, isolating this one change) and the fix WORKED:
        HIV_gp41 B-cell epitopes:  0 -> 1
        HIV_p17  B-cell epitopes:  0 -> 1
    THE RESCUED gp41 EPITOPE IS ITSELF EXPERIMENTALLY VALIDATED: Phase 1H
    (re-run against the new construct) finds VWGIKQLQARVLAVER
    CONTAINED_IN_CURATED with MHC-ligand-elution assay evidence, PMID
    12552005 -- confirming this was a real, previously characterised epitope
    the old tie-break had discarded, not a hypothetical concern.
    EVERY OTHER MEASURE HELD OR IMPROVED: 0 bad hydrophobic windows (both),
    0 spurious linker motifs (both), instability 37.65->38.27 (both <=40,
    negligible), GRAVY -0.438->-0.500 (both well under the 0.4 ceiling), pI
    9.39->9.32 (both outside the avoid-band). The junction-cysteine problem
    (G5, below) went from 4 implicated sites to ZERO.
    STATE THE RULE EXPLICITLY IN METHODS: when candidate epitopes from
    different classes overlap the same region, B-cell and MHC-II candidates
    are retained in preference to MHC-I. This is a stated design choice
    justified by immunological role, not an artifact.
    THE IRONY IS STILL WORTH REPORTING: deviation #24 was written to stop
    gp41 losing its B-cell block to an over-strict allergenicity rule. It
    succeeded there, and the block was then lost at assembly to a different,
    unrelated mechanism -- illustrating why every stage needs its own check
    rather than trusting that an earlier fix protects a later stage.

E1. TOOLS_INSTALL.txt as previously written would NOT have reproduced a

E2. ToxinPred2 and HemoPI2 CANNOT share an environment with the Phase 2 stack
    (pandas 1.x vs pandas 3.x conflict). They now live in a dedicated
    environment. ToxinPred2 also carries a genuine scope bug that fires only
    when BLAST returns no toxin hits -- which is exactly this study's case --
    and has been patched.

E6. NetSurfP-3.0's live web download does not match the format the parser
    was originally written against. The real download is tab-delimited with
    no header row of column names (only a positional comment block), and
    carries no discrete secondary-structure letter column at all -- only
    raw per-residue probabilities for helix/strand/coil. The parser now
    derives the discrete call as argmax of the three probabilities (the
    standard way to harden a 3-way softmax into a class), with the original
    comma/q3-column parser kept as a fallback for a possible future format.
    Also fixed a related crash: a citation line inside the file's own
    comment block contains real commas, which broke a naive CSV-parsing
    attempt outright rather than just misreading the data.

E5. ToxinPred2 -m 2 crashes on a batch of EXACTLY ONE sequence with an
    ONNX rank-mismatch error. Root cause: np.loadtxt() returns a 1D array for
    a single-row feature CSV, 2D for 2+ rows, and the model always requires
    rank 2. Every earlier use of this tool in the project submitted 2+
    sequences at once, so this never surfaced until Phase 2A's construct-
    level check (which submits exactly one sequence: the whole assembled
    vaccine). Patched with a one-line np.atleast_2d() wrap in both conda
    environments carrying the tool.
    ALSO: Phase2A_secondaryScreening.py's default ToxinPred2 binary path
    pointed at the WRONG conda environment (phase2, whose copy was
    deliberately reverted to unpatched upstream during the Phase 1Ea fix) --
    corrected to point at toxtools_env, matching Phase 1Ea.

E4. Phase 1H stalls for ~18 minutes per run on any NAT64 network. getaddrinfo
    returns a synthesised IPv6 address for query-api.iedb.org whose SYN is
    never answered, and requests/urllib3 has no Happy Eyeballs, so every page
    pays the full fallback delay. Measured: 60.7 s per request as-is vs 0.6 s
    with IPv4 forced -- a 100x difference. The step now forces IPv4 for its
    own requests. It presents as 0% CPU "slow work", the same false signature
    as the documented Entrez socket-timeout trap.

E3. MHCnuggets required a source patch to run at all on a current Keras. It
    calls Adam(lr=0.001); Keras 3 removed the `lr` alias. WITHOUT THE PATCH
    THE FAILURE IS SILENT AND DANGEROUS: the step exits 0, prints SUCCESS,
    writes valid files, and every MHC-II peptide receives zero binding alleles
    and 0.0% population coverage. That zero reads as a plausible biological
    finding. This affected the first run of Phase 1F and was caught only by
    checking that the tool had actually run.
    After the fix: MHC-II peptides reaching >=90% coverage went from 0 to 8,
    and 32 of 33 class-II alleles contribute.
    Also note: alleles must be passed to MHCnuggets WITHOUT the asterisk, or
    every allele silently falls back to the same default model.
